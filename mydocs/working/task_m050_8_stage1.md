카드 상세·시세 추이를 포함한 API 계약을 확정하고, 검색·최신가·추이·순위 쿼리 초안을 측정해 쿼리 형태와 인덱스 추가 여부를 정한다. 이 단계는 문서만 작성했고 `src/`는 바꾸지 않았다.

### 2. 측정 환경

| DB | 내용 |
|----|------|
| 개발 DB (`cardmarket`) | 카드 37,307장, 변형 53,446개, 시세 117,746행 (TCGCSV 11-22·23, Cardmarket 11-23·24). 읽기만 함 |
| 측정용 `poc_task8` | 개발 DB 복제 + 가격 이력을 날짜만 바꿔 **365일치로 복제** (30,216,617행, `price_history` 4.7 GB), 환율 평일 1년치. 검색 인덱스 시안 추가 |

- 365일치 생성 중 처음 방식(외래 키·인덱스를 둔 채 3천만 행 INSERT)이 1시간 가까이 끝나지 않아 취소하고, 외래 키·인덱스를 떼고 넣은 뒤 다시 만들었다(INSERT 1분 49초, 인덱스 약 1분).

### 3. 검색 (A1·A2)

**처음 안**: 낱말마다 `ILIKE '%낱말%'`(카드 이름·세트 이름), 세트 ID, 번호, 한글 종 이름을 OR로 묶고, 모든 낱말이 맞는지 `NOT EXISTS (unnest(낱말))`로 확인 → 낱말 배열을 쓰면 trigram 인덱스를 쓸 수 없어 카드 전체를 훑는다.

| 검색어 | 처음 안 | 확정 안 (`poc_task8`) |
|--------|--------:|--------:|
| `pikachu` | 209 ms | 8~11 ms |
| `피카츄` | 149 ms | 8~11 ms |
| `피카츄 ex` | 102 ms | 8~11 ms |
| `sv03.5 25` | 83 ms | 7~10 ms |
| `ピカ` (2자, `ja`) | 34 ms | 34~48 ms |
| `리자몽` | 97 ms | 7~10 ms |
| `25` (번호만) | 98 ms | 32~45 ms |
| `a` (1자, 23,001장 일치) | 110 ms | 123~189 ms |

- 원인: 이 DB(Alpine, `en_US.utf8`)에서는 `lower()`·`ILIKE`가 카드 3만 7천 장을 훑을 때 조건 하나에 약 25~35 ms씩 든다. 조건이 여럿이라 100 ms를 넘었다.
- **확정 안**: 가장 긴 낱말 하나로 **후보 카드를 인덱스로 먼저 찾고**(이름 trigram, 세트 ID 목록, 번호, 도감 번호 GIN의 UNION), 나머지 낱말은 후보에서만 확인한다. 이를 위해 인덱스 2개가 필요하다.
  - `cards_name_lower_trgm_idx`: `gin (lower(name) gin_trgm_ops)`. 저장 열(`search_name` 생성 열)도 시험했는데 7 ms 대 10 ms로 차이가 작아, 테이블을 바꾸지 않는 식 인덱스로 정했다.
  - `cards_local_number_idx`: `btree (ltrim(local_id, '0'))`. 번호만으로 찾을 때(`25` = `025`) 쓴다.
- 결함 발견: 처음 안에서 `c.dex_ids && 종목록`이 트레이너스·에너지(`dex_ids` NULL)에서 NULL이 돼 `NOT (...)`가 거짓이 되지 않아 모든 트레이너스 카드가 맞는 것으로 나왔다(`피카츄 ex` 6,885장 → 수정 후 50장). 확정 안은 `coalesce(..., false)`로 막았고, 2단계 테스트에 넣는다.
- `total`은 `count(*) OVER ()`로 같은 쿼리에서 구한다. 후보가 적어 따로 세는 쿼리보다 낫다.
- 한 글자 검색(`a`)은 2만 장이 맞아 정렬에 시간이 든다(약 120~190 ms). 계약상 1자도 허용하므로 그대로 두고, 실사용에서 문제가 되면 #11에서 다룬다.

### 4. 최신가·대표가 (A3·A4)

변형 × 판매가 소스마다 `LATERAL`로 최신 1행(`price_history_pkey` 역순), 환율도 `LATERAL`로 직전 1행(`fx_rates_pkey` 역순).

| 쿼리 | 개발 DB | `poc_task8` (1년) |
|------|--------:|--------:|
| 카드 24장(검색 한 쪽)의 변형 × 소스 최신가 + 원화 | 2~3 ms | 첫 실행 20 ms, 이후 2 ms |

- 대표가(Q1)는 이 결과에서 Go가 고른다. 검색·상세·순위 모두 같은 쿼리를 쓴다.

### 5. 시세 추이 (A5)

카드의 모든 변형 × 소스, 기간 시작일 이후, 환율 `LATERAL`(직전 값).

| 기간 | `poc_task8` 카드 10장 |
|------|--------:|
| `1y` (변형 2~4개 × 소스 2개, 약 700~1,460점) | 첫 실행 40~137 ms, 이후 17~46 ms |
| `30d` | 3~7 ms |

- 첫 실행이 느린 것은 디스크 읽기(1년치 4.7 GB에 `shared_buffers` 128 MB) 때문이다. 캐시된 뒤에는 목표 안이다.

### 6. 급등·급락 순위 (A6)

| 안 | 내용 | 7d | 30d |
|----|------|----:|----:|
| (a) | 비교일을 순위 전체에 하나로 정함 (기준일 − N 이하 가장 가까운 TCGCSV 날짜), 기준일 행 → 비교일 행을 기본 키로 하나씩 조회 | 228~303 ms | 233~251 ms |
| (b) | 변형마다 비교일 이전 가장 가까운 가격을 `LATERAL`로 조회 | 310~640 ms | 1,036 ms |
| **(c) 확정** | (a)와 같은 비교일. 기준일·비교일 행을 각각 보조 인덱스 `price_history_source_id_price_date_idx`(Index Only Scan)로 읽어 해시 조인 (`MATERIALIZED` CTE) | **59~91 ms** | **60~77 ms** |

- (a)·(c)는 결과가 같다. (a)는 플래너가 비교일 1.9만 행마다 기본 키를 찾는 중첩 루프를 골라 디스크를 많이 읽었다.
- 수행 계획서 Q3의 "그날 없으면 그 이전 가장 가까운 날"은 **순위 전체에 비교일 하나**로 적용한다(계약에 명시). 변형마다 찾는 (b)는 느리고, TCGCSV는 하루에 전체 그룹을 받으므로 날짜 단위 공백이 대부분이다.
- 상승은 0보다 큰 것만, 하락은 0보다 작은 것만 넣는다. 카드당 1개를 고른 뒤 정렬한다.

### 7. Q6 목표 대비

| 엔드포인트 | 목표 | 측정 (캐시 후) | 판단 |
|------------|------|----------------|------|
| 검색 | p95 100 ms | 대부분 8~48 ms, 1자 검색 120~190 ms | 인덱스 2개를 더하면 충족 (1자 예외) |
| 상세 (최신가) | p95 100 ms | 2 ms | 충족 |
| 추이 1y | p95 100 ms | 17~46 ms (첫 실행 최대 137 ms) | 충족, 캐시 없을 때 넘을 수 있음 |
| 순위 | 300 ms | 59~91 ms (확정 안) | 충족 |

실제 응답 시간(HTTP 포함, 100회 p50·p95)은 5단계에서 개발 DB로 잰다.

## 제안

### 마이그레이션 `00005_search_indexes.sql` (2단계)

```sql
-- +goose Up
CREATE INDEX cards_name_lower_trgm_idx ON cards USING gin (lower(name) gin_trgm_ops);
CREATE INDEX cards_local_number_idx ON cards ((ltrim(local_id, '0')));
DROP INDEX cards_name_trgm_idx;   -- 대소문자를 구분하는 이름 인덱스. 검색이 lower(name) 을 쓰므로 쓰이지 않는다
-- +goose Down
CREATE INDEX cards_name_trgm_idx ON cards USING gin (name gin_trgm_ops);
DROP INDEX cards_local_number_idx;
DROP INDEX cards_name_lower_trgm_idx;
```

- `cards_name_trgm_idx`는 #4에서 이름 검색용으로 만들었고, `src/`의 어떤 쿼리도 쓰지 않는다(`ILIKE`·`LIKE` 사용 없음, 확인함). 지울지는 확인 사항 S1.
- 가격 쪽은 기존 인덱스(`price_history_pkey`, `price_history_source_id_price_date_idx`, `fx_rates_pkey`)로 충분해 추가하지 않는다.

## 발견 사항

- **오늘(11-25) 05:30 상시 수집이 실행되지 않았다.** Docker Desktop이 꺼져 있었고, 컨테이너는 12:16에 다시 떴다. 다음 실행은 11-26 05:30이다. 지금 TCGCSV 최신일은 11-23(11-22는 1,858행뿐), Cardmarket은 11-24다. 순위(7d)는 비교일이 없어 데이터가 쌓일 때까지 `items: []`가 된다. 수동 실행(`-once`, 약 2시간 40분)을 할지 정해 주시면 따른다. 2~3단계 개발에는 지장이 없다.
- 같은 변형도 소스 사이 가격 차이가 크다 (예: `ex6-74` Pikachu 리버스 홀로: TCGCSV $317.99, Cardmarket €90.75 / `ex4-43` 리버스: $198.84, €3.58). 상세·추이를 변형 × 소스로 나눠 보여 주는 이유이고, 연결 결함인지는 이 타스크 범위 밖이라 판단하지 않았다.
- 측정용 365일치 이력은 4.7 GB였다(#4 8절 추정과 같은 수준). `shared_buffers` 128 MB에서는 1년치 추이의 첫 조회가 디스크를 읽어 느려진다. 운영 설정(#11·#16)에서 다룰 사항이다.
