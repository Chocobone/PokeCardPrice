# Task #4: DB 스키마 설계 및 마이그레이션 — 수행 계획서

## 수행 목표

#2에서 확정한 데이터 소스와 #3에서 확정한 도구(goose, sqlc + pgx v5)를 바탕으로 **세트·카드·가격 소스·시세 이력·환율·사용자·컬렉션** 테이블을 설계하고 goose 마이그레이션으로 만든다.
#5(카탈로그 수집기), #6(해외 시세 수집기), #7(국내 거래가), #8~#10(API)이 테이블 구조를 다시 정하지 않고 바로 구현을 시작할 수 있는 상태를 만든다.

## 범위

1. **카탈로그**: 세트, 카드, 카드 변형(Normal·Holofoil·Reverse Holofoil 등). 카드 언어(`en`, `ja`, `ko`)와 한글판 → 일본판 연결(#7 A안)을 표현한다.
2. **소스·외부 ID**: 가격 소스(TCGCSV, TCGdex Cardmarket, 일본판 환산, 사용자 등록, 관리자 입력)와 소스별 외부 ID(TCGdex 카드 ID, TCGplayer `productId`+`subTypeName`, Cardmarket 상품 ID).
3. **시세 이력**: 카드 변형·소스·날짜 단위의 가격. 통화(`USD`·`EUR`·`KRW`), 원 가격, 가격 필드 종류(`market`·`avg`·`trend` 등), 가격 성격(`판매가`·`참고가(일본판 환산)`·`사용자 등록가`·`관리자 입력가`), 소스 갱신일, 수집일.
4. **환율**: 통화쌍, 값, 값 기준일, 제공처.
5. **사용자·컬렉션**: 사용자(비밀번호 해시 저장 컬럼까지, 인증 방식은 #9), 보유 카드·수량, 사용자 거래가(가격 KRW, 거래일, 상태 등급, 검증 상태. 판매자 정보 없음), 관리자 입력가의 출처·확인일.
6. **인덱스**: 카드·소스별 기간 조회(7일/30일/90일/1년), 최신가 조회, 이름·세트·번호 검색(#8)에 필요한 인덱스.
7. **sqlc 적용**: 금액(`numeric`)의 Go 타입과 `overrides`를 정하고, 각 테이블의 기본 쿼리(입력·조회) 일부를 작성해 코드 생성을 확인한다.
8. **문서**: 스키마 설계 문서(ERD, 테이블·컬럼 설명, 설계 결정 근거) 작성.

### 범위 밖

- 수집 작업 구현과 실제 데이터 적재 → #5, #6, #7
- API 핸들러와 비즈니스 쿼리 전체 → #8, #9, #10 (해당 타스크가 필요한 쿼리를 추가한다)
- 인증 토큰·세션 저장 방식 → #9 (필요하면 #9에서 마이그레이션을 추가한다)
- 캐시, 집계 테이블·구체화 뷰 → #11
- 시세 이력 파티셔닝 (데이터 규모 추정 결과 필요하다고 판단될 때만 구현 계획서에서 다시 제안)

## 핵심 설계 원칙

- **원 가격 보존**: 수집한 가격은 원래 통화·원래 값 그대로 저장하고, 원화 환산은 환율 테이블과 조회 시점에 계산한다. 단, #7 A안의 `참고가(일본판 환산)`처럼 환산 결과 자체가 가격인 경우는 KRW로 저장하고 사용한 환율 기준일을 남긴다.
- **가격 성격 구분**: 실거래가·판매가·참고가가 섞여 보이지 않도록 모든 가격 행에 가격 성격을 둔다 (#8, #13이 이 값으로 표시를 나눈다).
- **멱등 적재**: 같은 카드 변형·소스·가격 필드·날짜의 가격은 한 행만 존재하도록 유일 제약을 두어, 수집기를 다시 실행해도 중복이 생기지 않게 한다 (`ON CONFLICT` 사용).
- **금액은 `numeric`**: 부동소수점 오차를 피한다. Go 타입은 구현 단계에서 후보(`pgtype.Numeric`, 문자열, decimal 라이브러리)를 실제 sqlc 생성 코드로 비교해 정한다.
- **열거 값 표현**: PostgreSQL `enum` 타입과 `text` + `CHECK` 제약을 비교해 정한다 (값 추가 시 마이그레이션 비용, sqlc 생성 타입 기준).
- **되돌리기 가능**: 모든 마이그레이션에 `Down`을 작성하고 `up → down → up`을 검증한다.
- **설계 승인 후 구현**: ERD와 테이블 정의를 먼저 문서로 제시하고, **작업지시자 승인 후에** 마이그레이션 SQL을 작성한다.

## 위험과 대응

| 위험 | 대응 |
|------|------|
| TCGdex `variants_detailed`가 문서에 없는 필드라 변형 구분이 바뀔 수 있음 | 변형을 외부 필드에 묶지 않고 자체 변형 테이블로 두며, 외부 ID는 별도 테이블에서 연결한다 |
| 한글판·일본판 세트 코드·번호 일치 범위가 미확인 (#5 확인 예정) | 카드 간 연결을 별도 컬럼(또는 테이블)으로 두어 자동 매칭이 실패해도 수동 연결이 가능하게 한다 |
| 시세 이력 행 수가 커짐 (카드 수만 장 × 변형 × 소스 × 필드 × 일수) | 2단계에서 행 수를 추정하고, 인덱스 크기를 확인해 파티셔닝 필요 여부를 판단한다 |
| #9 인증 방식이 정해지지 않음 | 사용자 테이블은 식별자·이메일·비밀번호 해시·생성일 등 최소 컬럼만 두고, 나머지는 #9에서 추가 마이그레이션 |
