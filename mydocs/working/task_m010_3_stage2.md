# Task #3 단계2 완료 보고서: DB 접근 방식·마이그레이션 도구 비교

## 수행 내용

pgx v5.12.0, sqlc v1.31.1(+pgx), GORM v1.31.2로 같은 저장소 인터페이스를 구현하고, 같은 테스트 6개를 compose `db`의 임시 데이터베이스 `poc_task3`에서 실행했다.
golang-migrate v4.20.1과 goose v3.29.0으로 같은 마이그레이션을 만들어 up·down, 동시 실행, 실패 처리를 비교했다. sqlc가 두 도구의 마이그레이션 파일을 스키마로 읽는지도 확인했다.

결과는 `mydocs/tech/backend_stack.md`의 "2. DB 접근 방식", "3. 마이그레이션 도구" 절에 정리했다.

## 발견 사항

1. **sqlc 생성기는 CGO 없이 컨테이너에서 실행된다.** `go run`으로 첫 실행 85초, 이후 2.5초이다. 개발 이미지를 바꾸지 않아도 된다.
2. **sqlc는 마이그레이션 디렉터리를 스키마로 읽는다.** golang-migrate·goose 형식 모두 최종 스키마로 코드를 생성했다. 스키마 파일을 따로 둘 필요가 없다.
3. **sqlc는 없는 컬럼을 생성 단계에서 잡는다.** `nam` 오타가 `column "nam" does not exist`로 보고되었다.
4. **sqlc 기본 타입은 `pgtype.Numeric`, `pgtype.Date`이다.** `overrides`로 `*string`, `time.Time`을 지정해 해결했다. 금액 타입은 #4에서 정해야 한다.
5. **golang-migrate는 실패 후 dirty 상태로 남는다.** 실제 스키마는 롤백되었는데 버전은 3으로 표시되어, `Force(2)`로 되돌려야 했다.
6. **goose는 잠금 없이도 동시 실행 오류가 없었다.** 원인은 확인하지 않았다. 사용 시 세션 잠금을 켠다.

## 잠정 판단

- DB 접근: **sqlc** (pgx 런타임). 생성 코드로 어려운 쿼리는 pgx 직접 사용
- 마이그레이션: **goose**
- GORM은 제외

선정은 3단계에서 확정한다.

## 계획과 달라진 점

- sqlc 생성기 실행 방법은 `go run` 하나만 시험했다. 동작에 문제가 없어 개발 이미지에 설치하는 방법이나 별도 컨테이너는 비교하지 않았다.
- 동시 실행은 계획의 2개 대신 3개로 10회 반복했다. 1회로는 경합이 드러나지 않을 수 있어서이다.
- sqlc가 마이그레이션 파일을 읽는지 확인하는 항목을 실제 생성으로 확인했다.
