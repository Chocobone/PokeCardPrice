# Task #3: 백엔드 기술 선정 — 수행 계획서

## 수행 목표

Go 백엔드의 **웹 프레임워크, DB 접근 방식, 마이그레이션 도구, 스케줄러 방식**을 비교해 확정하고, 확정한 기술을 #1의 백엔드 골격에 적용한다.
#4(DB 스키마)와 #6(시세 수집 스케줄러)가 도구 선택 없이 바로 구현을 시작할 수 있는 상태를 만든다.

## 범위

1. **웹 프레임워크**: Gin, Echo를 비교한다. 비교 기준선으로 표준 라이브러리 `net/http`(Go 1.22 이후 메서드·경로 변수 패턴 지원)도 함께 놓는다.
2. **DB 접근 방식**: pgx(직접 SQL), sqlc(SQL → Go 코드 생성, pgx 기반), GORM(ORM)을 비교한다.
3. **마이그레이션 도구**: golang-migrate, goose를 중심으로 비교하고, 조사 중 더 적합한 후보가 나오면 추가한다.
4. **스케줄러 방식**: API 서버 내장(고루틴과 `time.Ticker` 또는 cron 라이브러리)과 별도 수집 프로세스(같은 모듈의 두 번째 진입점, 별도 컨테이너)를 비교한다.
5. **골격 적용**: 확정한 기술을 `src/backend/`에 도입한다.
   - 라우터 교체와 기존 `/healthz` 테스트 유지
   - DB 연결 풀, `/healthz`에 DB 상태 확인 추가 (#1 후속 사항)
   - 마이그레이션 실행 방법과 빈 초기 마이그레이션 (테이블 설계는 #4)
   - 스케줄러 진입점 골격 (실제 수집 작업은 #5, #6)
   - CLAUDE.md `빌드 및 실행` 절에 마이그레이션·수집기 실행 명령 추가

### 범위 밖

- 테이블 설계와 실제 마이그레이션 내용 → #4
- 수집 작업 구현 → #5, #6, #7
- 인증 방식·라이브러리 → #9
- 캐시 방식 → #11
- 운영 배포 이미지 → #16

## 비교 기준

각 항목을 다음 순서로 판단한다.

1. **요구 적합성**: #2에서 정한 수집 구조(하루 1회 수집, 소스별 요청 간격, 시계열 조회)와 이슈 #8~#11 API를 무리 없이 구현할 수 있는가
2. **유지 상태**: 최신 릴리스, Go 1.27 호환, 활동 중인 저장소인가
3. **학습·구현 비용**: 텀프로젝트 일정에서 익히고 디버깅하기 쉬운가, 의존성이 적은가
4. **테스트 용이성**: 핸들러와 DB 접근을 단위 테스트하기 쉬운가

## 핵심 설계 원칙

- **실제 확인**: 문서 비교에 그치지 않고, 후보마다 같은 최소 예제를 컨테이너의 Go 1.27로 빌드해 동작을 확인한다. 예제는 세션 임시 폴더에 두고 저장소에 넣지 않는다.
- **선정과 적용 분리**: 비교 결과로 선정안을 제시하고 **작업지시자 승인 후에** 골격에 적용한다.
- **의존성 최소화**: 기능이 같으면 의존성이 적은 쪽을 고른다. 표준 라이브러리로 충분하면 프레임워크를 들이지 않는 선택지도 열어 둔다.
- **버전 고정**: 도입하는 모듈은 `go.mod`에 버전을 고정하고, 선정 문서에 버전과 확인일을 남긴다.
- **기존 동작 유지**: `/healthz` 응답과 기존 테스트 3개, 정상 종료 동작을 유지한다.

## 위험과 대응

| 위험 | 대응 |
|------|------|
| 후보 라이브러리가 Go 1.27과 호환되지 않음 | 빌드 결과를 기록하고 후보에서 제외하거나 대안 버전을 찾는다 |
| sqlc 코드 생성 도구를 컨테이너에서 실행해야 함 | `go run`으로 실행하는 방법과 개발 이미지에 설치하는 방법을 비교해 구현 계획서에 정한다 |
| 스케줄러를 별도 프로세스로 정하면 compose 구성이 바뀜 | `Docker/` 변경을 구현 단계에 포함하고 재현성(`down` → `up --build`)을 다시 검증한다 |
