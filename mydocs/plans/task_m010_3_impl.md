1~3단계는 비교 조사이며 저장소의 소스 코드를 바꾸지 않는다. 4단계에서만 `src/backend/`, `Docker/`, `CLAUDE.md`를 변경한다.

## 공통 규칙

### 비교 예제 (PoC)

- 예제 코드는 **세션 임시 폴더**에 두고 저장소에 넣지 않는다. 결과 문서에는 측정값과 필요한 코드 발췌만 남긴다.
- 예제는 기존 `backend` 컨테이너와 같은 이미지(`golang:1.27-alpine3.24`)에서 빌드·실행한다. 임시 폴더를 바인드 마운트한 일회성 컨테이너(`docker compose run --rm`)를 쓴다.
- DB 예제는 compose의 `db` 서비스에 **임시 데이터베이스 `poc_task3`**를 만들어 사용하고, 단계가 끝나면 삭제한다. 기존 개발 DB에는 손대지 않는다.
- 모듈 버전은 조사 시점의 최신 안정 버전을 쓰고 문서에 버전과 확인일을 남긴다.

### 공통 측정 항목

| 항목 | 측정 방법 |
|------|-----------|
| Go 1.27 빌드 | `go build ./...`, `go vet ./...` 성공 여부 |
| 의존성 수 | `go list -m all` 줄 수 (직접·간접 포함) |
| 바이너리 크기 | `go build -ldflags="-s -w"` 결과 크기 |
| 코드 양 | 같은 기능을 구현한 예제의 줄 수 (`gofmt` 후, 테스트 제외) |
| 테스트 | 같은 시나리오의 테스트를 작성해 통과 여부와 작성 편의 비교 |
| 유지 상태 | 최신 릴리스 날짜, 저장소 최근 커밋, 공식 문서의 지원 Go 버전 |

성능 벤치마크는 하지 않는다. 이 서비스의 부하(하루 1회 수집, 텀프로젝트 규모 조회)에서는 후보 간 성능 차이가 판단에 영향을 주지 않는다고 본다.

## 2단계: DB 접근 방식·마이그레이션 도구 비교

### 목표

pgx, sqlc, GORM 중 DB 접근 방식과 마이그레이션 도구를 고를 근거를 만든다.

### 구현

**DB 접근 예제.** #2의 설계 입력을 축소한 테이블 2개(`cards`, `price_history`)로 같은 작업을 구현한다.

| 작업 | 내용 | 확인하려는 점 |
|------|------|---------------|
| 단건 조회 | 카드 ID로 조회, 없으면 not found 구분 | 오류 처리 |
| 일괄 저장 | 가격 1,000건 저장 | 대량 삽입 방법(`COPY` 등)과 소요 시간 |
| 업서트 | 같은 카드·날짜·소스면 갱신 (`ON CONFLICT`) | 수집기의 재실행 안전성 |
| 시계열 조회 | 카드 하나의 기간별 일평균가 (`date_trunc`, 집계) | 복잡한 SQL 표현력 |
| 트랜잭션 | 카드와 가격을 한 트랜잭션으로 저장, 실패 시 롤백 | 트랜잭션 API |
| NULL·숫자 | NULL 가격, `numeric` 가격 값의 Go 타입 매핑 | 금액 정밀도 |
| 테스트 | 실제 DB(`poc_task3`)에 대한 통합 테스트 | 테스트 구성 비용 |

- 연결 풀은 세 후보 모두 pgx 드라이버를 기준으로 맞춘다(GORM은 `gorm.io/driver/postgres`가 pgx를 사용).
- sqlc는 코드 생성기 실행 방법(`go run`, 개발 이미지에 설치, 별도 컨테이너)을 함께 비교한다.

**마이그레이션 예제.** golang-migrate, goose로 같은 마이그레이션 2개(테이블 생성, 컬럼 추가)를 만든다.

| 항목 | 확인 내용 |
|------|-----------|
| 파일 형식 | SQL 파일 형식, up/down 구성 |
| 실행 방식 | CLI, Go 라이브러리 호출, `go:embed`로 바이너리에 포함 가능 여부 |
| 컨테이너 실행 | compose 환경에서 실행하는 명령 |
| 동시 실행 | 두 프로세스가 동시에 실행할 때 잠금 동작 |
| 실패 처리 | 중간에 실패한 마이그레이션의 상태와 복구 방법 |
| sqlc 연동 | sqlc가 마이그레이션 파일을 스키마로 읽을 수 있는지 |

## 4단계: 선정 기술을 백엔드 골격에 적용

### 목표

승인된 선정안을 `src/backend/`에 도입해, #4와 #6이 바로 구현을 시작할 수 있게 한다.

### 구현

아래는 예상 구조이며, 3단계 선정 결과에 따라 이름과 구성이 바뀔 수 있다. 바뀌면 단계 보고서에 기록한다.

```
src/backend/
├── cmd/
│   ├── server/main.go        ← 라우터 교체, DB 연결 풀 생성·종료
│   └── collector/main.go     ← (B 방식 선정 시) 수집기 진입점 골격
├── internal/
│   ├── server/               ← 선정 프레임워크로 라우팅, /healthz DB 확인
│   ├── db/                   ← 연결 풀 생성, (sqlc 선정 시) 생성 코드와 쿼리 파일
│   └── scheduler/            ← 일정 등록·정상 종료 골격, 실제 작업은 빈 함수
└── migrations/               ← 빈 초기 마이그레이션 1개 (테이블 설계는 #4)
```

| 변경 | 내용 |
|------|------|
| `/healthz` | DB `Ping` 결과를 포함한다. 정상이면 200 `{"status":"ok","db":"ok"}`, DB 실패면 503 `{"status":"degraded","db":"error"}`. 핸들러는 DB 의존성을 인터페이스로 받아 DB 없이 단위 테스트한다 |
| 기존 테스트 | 3개를 선정 프레임워크에 맞게 이식하고, DB 정상·실패 테스트 2개를 추가한다 |
| 설정 | `DATABASE_URL`이 없으면 시작 시 명확한 오류로 종료한다 |
| 정상 종료 | 서버, 연결 풀, 스케줄러를 순서대로 종료한다 |
| 마이그레이션 | 선정 도구로 실행하는 명령을 정하고, 빈 초기 마이그레이션으로 up/down을 확인한다 |
| `Docker/` | B 방식 선정 시 `collector` 서비스 추가. 엔트리포인트·도구 설치가 필요하면 Dockerfile 수정 |
| `CLAUDE.md` | `빌드 및 실행` 절에 마이그레이션 실행, (sqlc 선정 시) 코드 생성, 수집기 실행·수동 실행 명령 추가 |
| `README.md` | 실행 방법에 바뀐 부분이 있으면 반영 |

### 검증

| 항목 | 방법 |
|------|------|
| 빌드·정적 검사 | `go build ./...`, `go vet ./...`, `gofmt -l` 결과 없음 |
